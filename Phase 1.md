# Phase 1 — Session Data Layer

Status: **complete and verified**
Date: 2026-09-02
Branch: `native/phased-rewrite`
Preceding commit: `a1d1e21` (Phase 0 audit correction)

---

## Objective

Make session persistence correct before any session behaviour exists. Phase 1 defines how a focus
session is represented durably, how it is stored in SQLite, and the smallest repository contract
the later phases genuinely need — with no timer, no transitions, and no workflow.

## Implemented scope

- `SessionId`: stable, typed application identity.
- `SessionType` (Work, Break) and `SessionStatus` (Running, Completed, Stopped, Interrupted), each
  with explicit, validated text mapping in both directions.
- `SessionRecord`: the persisted record, with UTC normalization and shape invariants.
- Three narrow persistence exceptions: not found, duplicate identity, active session already
  exists.
- `ISessionRepository`: five operations, each justified below.
- `SqliteSessionRepository`: the implementation, one short-lived pooled connection per operation.
- Schema migration 2 (`sessions`) applied through the Phase 0 migration mechanism, including
  storage-enforced invariants and two indexes.
- `SqliteConnectionFactory.OpenConnectionAsync` so the repository is cancellation-aware end to end.
- 116 new tests covering round-trips, invalid stored values, invariants, boundaries, ordering, and
  migration from a real Phase 0 database.

Not implemented, on purpose: nothing starts, stops, completes, interrupts, or times a session.

## Data model

One row per session in `sessions`. Every column is a raw fact; nothing stored is derived from
another session, and nothing aggregated is stored at all.

| Field | C# | SQLite | Meaning |
| --- | --- | --- | --- |
| `Id` | `SessionId` | `id TEXT` (36 chars) | Stable identity, generated before the row exists |
| `Type` | `SessionType` | `type TEXT` (`work`/`break`) | Which kind of session this is |
| `Status` | `SessionStatus` | `status TEXT` | `running`, `completed`, `stopped`, or `interrupted` |
| `StartedAt` | `DateTimeOffset` (UTC) | `started_at_utc TEXT` (28 chars) | The instant the session began |
| `PlannedDuration` | `TimeSpan` | `planned_duration_seconds INTEGER` | The length it was started for |
| `EndedAt` | `DateTimeOffset?` (UTC) | `ended_at_utc TEXT` nullable | The instant it stopped being active; null exactly while Running |
| `CreatedAt` | `DateTimeOffset` (UTC) | `created_at_utc TEXT` (28 chars) | When the row was first written |

Two values are **computed, never stored**:

- `PlannedEndAt` = `StartedAt + PlannedDuration`
- `ActualDuration` = `EndedAt - StartedAt` (null while Running)

The product specification sketches both as columns. They are exact functions of stored facts, so
storing them would create two ways for one database to disagree with itself — the classic source of
"the report says 4 sessions but the list shows 3". Keeping one source of truth per fact removes that
failure mode entirely, and both values remain part of the public API, so callers see no difference.

## Invariants

Each of these is enforced twice: in `SessionRecord.Validate()` before a write, and by SQLite so
durable state cannot drift even if something writes around the repository.

| Invariant | In code | In storage |
| --- | --- | --- |
| Identity is present | `Id.IsEmpty` rejected | `id` is the primary key, `length(id) = 36` |
| Type is a known value | `Enum.IsDefined` | `CHECK (type IN ('work','break'))` |
| Status is a known value | `Enum.IsDefined` | `CHECK (status IN (…4 values…))` |
| Planned duration is meaningful | must be `> 0` | `CHECK (planned_duration_seconds > 0)` |
| Planned duration is storable without loss | must be whole seconds | column is `INTEGER` in a `STRICT` table |
| Running means "no end yet" | Running ⇒ `EndedAt` null; finished ⇒ `EndedAt` set | `CHECK ((status = 'running') = (ended_at_utc IS NULL))` |
| A session cannot end before it starts | `EndedAt >= StartedAt` | `CHECK (ended_at_utc IS NULL OR ended_at_utc >= started_at_utc)` |
| Timestamps are canonical | written through `UtcTimestamp` | `CHECK (length(...) = 28)` on each timestamp column |
| **At most one session is Running** | repository checks inside an immediate transaction | `CREATE UNIQUE INDEX ux_sessions_single_running ON sessions (status) WHERE status = 'running'` |

Two notes on deliberate non-invariants:

- A zero-length finished session is legal (`EndedAt == StartedAt`). Stopping a session the instant
  it starts is a real thing a user can do, and the data layer should record it rather than argue.
- Nothing here constrains *which status may follow which*. That is workflow, and it belongs to the
  Session Engine.

## Identity strategy

`SessionId` wraps a `Guid` (v4, `Guid.NewGuid()`) and persists as its canonical 36-character
lowercase form.

- **Generated by the application, before the row exists.** The specification requires a session to
  be durable from the moment it begins; having the identity first means the session can be logged
  and referenced without a round-trip to storage.
- **SQLite `rowid` is never application identity.** A row number is a storage artefact: it carries
  ordering meaning it should not, and it is not stable across a rebuild or an export.
- **Survives everything that matters**: reload, repository recreation, restart, and any future
  projection, because the value is the identity rather than a pointer to a location.
- `Guid.Empty` is rejected by the constructor, and `default(SessionId)` reports `IsEmpty` so the one
  hole a struct leaves cannot reach storage.
- A time-ordered UUID (v7) was considered and rejected: it would imply that identity carries time
  semantics, and ordering must come from the timestamp columns, which are the actual facts.

## Time strategy

**In C#:** `DateTimeOffset`, always UTC. `SessionRecord` normalizes on construction, so a record
built from a local or offset-bearing value still exposes UTC. `DateTime` is avoided entirely — its
`Kind` is easy to lose and impossible to see in a debugger without checking.

**In SQLite:** `TEXT` in one canonical form, `yyyy-MM-ddTHH:mm:ss.fffffffZ` (28 characters), written
and read only through `UtcTimestamp`.

**Normalization policy:** convert to UTC at the boundary, store UTC, return UTC. No local time and
no offset ever reaches storage, so no stored value depends on the machine's time zone.

Why this choice fits what is coming:

- **Restart and crash recovery** compare a stored instant against the current instant. Both are
  unambiguous UTC, so the comparison needs no context.
- **Sleep/resume** works for the same reason: a session's planned end is an absolute instant, not a
  countdown that has to keep ticking.
- **DST and time zones** cannot corrupt anything. A session that spans a DST change still has the
  correct elapsed time, because UTC has no discontinuities. Turning instants into local days is a
  presentation concern, and Reports will do it against raw records.
- **Reporting by day** is served by range queries over instants; the caller decides which instants
  bound its day, which is what makes both a UTC day and a local day expressible.
- **Deterministic tests** are possible because the format is exact to a .NET tick, so round-trips
  compare equal rather than approximately equal.
- **Sortable as plain text**, so SQLite compares timestamps correctly without date functions, and
  the `started_at_utc` index is usable for ranges.

## Duration strategy

**Planned duration** is stored as whole seconds in an `INTEGER` column. Integers only — no
floating-point duration is ever written, so no value can drift by a fraction on a round-trip.

A planned duration must be positive and a whole number of seconds; a sub-second value is rejected
rather than silently truncated by the cast to seconds. Seconds (not minutes) is the unit because the
product's own defaults are minutes but nothing should force a future preset to be a whole minute.

**Actual duration** is not stored at all; it is `EndedAt - StartedAt`, so it inherits full tick
precision from the two timestamps and can never disagree with them.

## SQLite schema

Applied as migration 2, named `sessions`:

```sql
CREATE TABLE sessions (
    id                       TEXT    NOT NULL PRIMARY KEY,
    type                     TEXT    NOT NULL,
    status                   TEXT    NOT NULL,
    started_at_utc           TEXT    NOT NULL,
    planned_duration_seconds INTEGER NOT NULL,
    ended_at_utc             TEXT,
    created_at_utc           TEXT    NOT NULL,

    CHECK (length(id) = 36),
    CHECK (type IN ('work', 'break')),
    CHECK (status IN ('running', 'completed', 'stopped', 'interrupted')),
    CHECK (planned_duration_seconds > 0),
    CHECK (length(started_at_utc) = 28),
    CHECK (length(created_at_utc) = 28),
    CHECK (ended_at_utc IS NULL OR length(ended_at_utc) = 28),

    -- Running is exactly the state with no end timestamp.
    CHECK ((status = 'running') = (ended_at_utc IS NULL)),

    -- A session cannot end before it started.
    CHECK (ended_at_utc IS NULL OR ended_at_utc >= started_at_utc)
) STRICT;

CREATE UNIQUE INDEX ux_sessions_single_running
    ON sessions (status)
    WHERE status = 'running';

CREATE INDEX ix_sessions_started_at_utc
    ON sessions (started_at_utc);
```

Decisions worth naming:

- **`STRICT`** so SQLite's usual type flexibility cannot quietly store a number where text belongs.
  Values that are not losslessly the column's type are rejected.
- **Text codes rather than integers** for `type` and `status`. The database is a local file the user
  may open; `work` and `running` are self-describing, they survive any future enum renumbering, and
  a `CHECK` constraint on a small text set is exactly as strict as an integer would be.
- **A partial unique index** is what makes "only one session at a time" a property of storage rather
  than a promise made by code. Any number of finished sessions may share a status; only one row may
  be `running`.
- **One index on `started_at_utc`**, added because the repository exposes a start-time range read.
  No other index exists, because no other access pattern exists yet.
- **No settings table, no aggregate tables, no other future tables.**
- `WITHOUT ROWID` was considered for the text primary key and skipped: it changes storage layout for
  no measured benefit at this size.

## Migration

Phase 1 adds one entry to the existing `SchemaMigrations.All` list. Nothing bypasses the Phase 0
mechanism, and migration 1 was not edited — a shipped migration is frozen by definition.

`TargetVersion` is now **2**, derived from the list rather than written down twice.

| Starting state | What happens |
| --- | --- |
| No database file | Migrations 1 and 2 both apply; result reports `[1, 2]` and version 2 |
| Phase 0 database (`user_version = 1`) | Only migration 2 applies; result reports `[2]`, version 1 → 2 |
| Already at version 2 | Nothing applies; result reports an empty list and version 2 |
| Version newer than 2 | Initialization refuses to touch it and says why |

Each migration runs inside a `BEGIN IMMEDIATE` transaction that re-reads `user_version` before
acting, so the schema, its audit row, and the version bump commit together or not at all — a failed
migration cannot leave a half-created table behind.

The migration path is proven twice:

- **In tests**, by building a real Phase 0 database (applying migration 1 from the shipped list,
  writing its audit row, setting `user_version = 1`), then initializing and asserting the upgrade,
  the preserved Phase 0 audit row, and that session data written afterwards survives repeated
  initialization.
- **At runtime**, by launching the built application against the data root that the *Phase 0 build*
  had created earlier at schema version 1. The log shows `Applied database migration 2 (sessions).`
  with no re-application of migration 1, then `Database ready at schema version 2.` — a genuine
  in-place upgrade of a database this codebase did not create.

No test reaches a green state by deleting the database.

## Repository contract

`ISessionRepository` has five operations. Each one exists because a requirement that already exists
needs it — none is shaped for a future screen, and no SQL concept appears in the signature.

**`AddAsync(SessionRecord, CancellationToken)`**
The specification requires a session to be in the database from the moment it starts, not when it
finishes, so this is the first write of a session's life. Validates the record, then inserts.
Throws `DuplicateSessionIdException` for a repeated identity and
`ActiveSessionAlreadyExistsException` (carrying the id of the session already running) when the
record is Running and storage already holds one.

**`GetAsync(SessionId, CancellationToken)`**
Reads one session by identity. Returns `null` when it does not exist — absence is an ordinary answer
here, not an error. Rejects an empty id, because asking for nothing is a caller bug.

**`UpdateAsync(SessionRecord, CancellationToken)`**
Overwrites the stored row with the same id. A session's outcome becomes known in one step (it
finished, and here is when), so a whole-record write is the honest shape; narrow mutators like
"mark completed" would be workflow verbs and belong to Phase 2. Throws `SessionNotFoundException`
when the id is unknown, so a silent no-op update is impossible.

**`GetRunningAsync(CancellationToken)`**
Reads the single Running session or `null`. Recovery and coordination need exactly this question
answered, and storage guarantees the answer can never be ambiguous.

**`GetStartedBetweenAsync(fromInclusive, toExclusive, CancellationToken)`**
Raw records whose start falls in a half-open range. Returns records only — no totals, rates, or
groupings, because Phase 1 does not compute reports.

### Query semantics

The range is explicitly **`fromInclusive <= StartedAt < toExclusive`**. Half-open is the convention
that makes adjacent periods tile without gaps or double-counting: a session at exactly midnight
belongs to one day only. Both bounds are normalized to UTC before comparison, so a caller may pass
its own local day boundaries and get the instants it meant. `toExclusive` before `fromInclusive`
throws; an empty range returns an empty list.

Ordering is **`started_at_utc` ascending, then `id` ascending**. The tiebreaker exists so two
sessions with identical start instants still come back in a stable order rather than whatever the
storage engine felt like.

### Failure behaviour

Nothing is swallowed and no failure is dressed up as success. Duplicate identity, missing identity,
and "a session is already running" are translated into the three named exceptions because those are
conditions callers will reason about; every other SQLite failure propagates unchanged rather than
being flattened into a generic error. A stored value outside its canonical form throws
`FormatException` on read instead of being coerced into something plausible.

Writes that check before they write (`AddAsync`, `UpdateAsync`) run in a `BEGIN IMMEDIATE`
transaction, so the check and the write are atomic with respect to any other writer.

`Microsoft.Data.Sqlite`'s async methods are not truly asynchronous I/O — SQLite is synchronous — but
the contract is async because callers in the UI phases must not build blocking assumptions on it,
and because cancellation is then explicit at every call.

## Architecture decisions

**The session data layer lives in `FocusKey.Foundation`, under a `Sessions` namespace.** A second
assembly is not required by anything in this phase, and creating one now would be structure ahead of
need. The namespace boundary is already clean — `Sessions` depends on `Data`, never the reverse — so
extracting a `FocusKey.Core` project later is a mechanical move if the domain grows enough to earn
one.

**Enum plus explicit text mapper, not `Enum.Parse`.** `Enum.Parse` would accept `"1"`, accept
case variants, and silently follow a rename. The mappers are `switch` statements in both directions,
so an unknown stored value produces a `FormatException` naming the offending text, and an undefined
enum value cannot be written at all.

**Validation happens in the record, enforcement happens in the database.** `Validate()` gives
callers a clear `ArgumentException` before any I/O; the `CHECK` constraints and the partial unique
index mean that even a write that bypasses this code cannot leave storage in a state the domain
would refuse to read back. Tests prove both layers independently, including by inserting raw SQL
around the repository.

**A connection per operation, from the pooled factory.** No shared connection, therefore no shared
mutable state and no lifetime question to get wrong. Pooling keeps it cheap, and the Phase 0 pragmas
are applied on every open so no code path can forget them.

**Three exception types, not one and not a hierarchy.** Callers will genuinely branch on "already
running" versus "duplicate id" versus "not found"; anything else stays a raw failure. All three
derive from `InvalidOperationException`, so existing broad handlers behave sensibly.

**The one-active-session rule is enforced here, but not decided here.** Storage refuses to hold two
running rows. Deciding what to do when a user asks for a second session — refuse, stop the first,
show the active overlay — is Session Engine behaviour and is not in this phase.

**`SqliteConnectionFactory` gained an async open.** Without it the repository would open its
connection synchronously and cancellation would start one step late. The synchronous version stays,
because the bootstrapper runs at startup where async buys nothing.

## Known limitations

1. **Nothing in the application uses the repository yet.** The data layer is exercised by tests and
   the schema is created at startup, but no code path writes a session — by design, because writing
   one would be Phase 2 behaviour.
2. **No delete or purge operation.** Nothing in the product requires removing a session yet. When
   data retention becomes a real requirement it gets its own contract, rather than a speculative
   `DeleteAsync` sitting unused.
3. **`GetStartedBetweenAsync` returns every match with no paging.** For a personal focus tool a
   month of sessions is tens of rows; paging would be structure without a problem.
4. **Async is a contract, not real asynchrony.** `Microsoft.Data.Sqlite` executes synchronously; the
   async surface exists for callers and cancellation, and long operations will still occupy a thread.
5. **A `SessionRecord` whose `EndedAt` sits far in the future is storable.** Only the ordering rule
   is enforced; "an end timestamp should not be in the future" is a judgement the engine can make
   with a clock, and the data layer has no clock.
6. **Timestamp `CHECK` constraints test length, not shape.** A 28-character non-timestamp passes
   storage and fails on read with `FormatException` — proven by test. A `LIKE` pattern would catch it
   one step earlier at a per-write cost; the read-side failure is loud enough.
7. **The pre-existing `%LOCALAPPDATA%\FocusKey` database from the previous implementation still
   needs your decision** (carried over from Phase 0). It was never opened. On a real first launch,
   the new build would now add both `schema_migrations` and `sessions` to that file.
8. **Test temp directories may occasionally linger** in `%TEMP%\focus-key-tests`; pools are cleared
   on dispose, but a held handle never fails a test run.
